# Scaling Threshold beyond the published template

The published Esmeralda template admits at most **32 pledge records** per campaign, up to **8 stages**, and up to **5 reviewer keys per stage**. Pledgers do not all need to review delivery: the frozen stage terms name the reviewer keys and set a quorum from 1 up to the number of named reviewers. Votes are one per key, not weighted by sponsor contribution or pledge size. These are Threshold v1 code limits, not demonstrated Ootle consensus maxima. Existing ownerless campaigns cannot have their limits or terms changed.

The full 32-pledge cap was exercised on Esmeralda at epoch 11468: 31 community pledge records and one sponsor pledge registered, exact joint activation committed, and one private payout consumed all 32 stage cells. The recipient decrypted 32 tTARI; the indexer marked the component verified and the output verified and unspent. The signed payout was 6,912 bytes and cost 17,074 microtari. [The receipt and measurements](../evidence/scale32-metrics.json) are testnet evidence for this fixture, not a guarantee of throughput or costs in other conditions. The 31 community records used three keys, so the fixture does not establish 31 independent people.

For **100 community funders plus one sponsor**, a single-component design would require at least 101 pledge records. The least disruptive v2 candidate is to raise `MAX_PLEDGES` in a **new template** while retaining one confidential cell per owner per stage, exact per-role/per-stage Pedersen opening checks, one atomic activation, one transaction consuming all cells for each stage payout, and direct per-owner refunds. This keeps the core safety argument intact. Each additional pledge enlarges component state and the payout's native input set; activation work also grows with the selected set and number of stages. Ootle's pinned [native stealth limits](https://github.com/tari-project/tari-ootle/blob/v0.41.2/crates/engine_types/src/limits.rs) permit more than 101 inputs in a statement, but that limit alone does **not** prove the component can execute economically or within every network transaction, fee, and state limit at 101 records.

Before deploying a higher-cap template, test 64 and 101 pledges with actual compiled WASM in the pinned engine, including over-cap rejection, exact activation, late payout/refund conflict, and one owner refund after a partial release. Then submit staged capacity fixtures on Esmeralda, measure full signed bytes and fees, verify resulting component and UTXO state, and rerun from saved journals. Do not change the published v1 source and describe it as the same deployed binary; a new immutable template needs its own address and byte-identity evidence. An increased reviewer cap similarly requires a new template, explicit quorum validation, and tests of vote count and gas. Distinct reviewer keys still cannot prove independent humans.

If a single 101-input payout fails network limits, splitting a campaign into several independent 32-pledge campaigns would **weaken atomic bundle funding**: some cohorts could activate while others fail. A defensible sharded design would need a single Ootle main intent that activates every shard together under frozen per-shard budgets and a shared campaign commitment, plus an enforceable all-shard milestone payout or explicit disclosure that stage payments may settle separately. That multi-component atomic transaction and its refund/conflict behavior have not been implemented or tested. Pooling contributions into a few shared cells solely to reduce inputs would lose the current per-owner independent refund right unless a new on-chain claim proof is added. Neither a coordinator database nor a UI rule can replace those guarantees.

The three live capacity fixtures measure only transaction execution at 8, 16, and 32 records. No 100-funder capacity, unique-person identity, or production fee quote is claimed.
